## Sprint 89: Instance Identity Schema

**Role:** Schema Architect | **Layer:** Identity (1)

- `instance_metadata` — flexible key-value store

- Added `instance_id` foreign keys to `convergences` and `artifacts`
- RLS policies for public federation directory

### Key Decisions

1. **Single Local Instance** — Only one instance per deployment with `is_local = true`
2. **Trust Levels** — 4-tier model (unknown, untrusted, verified, trusted) for federation security
3. **Flexible Metadata** — JSON key-value store for extensibility without schema migrations
4. **Public Registry** — Instance info readable by anyone for discovery

- Domain hardcoded as `commons.id` in initialization; will need update mechanism for subdomains

## Sprint 90: Cross-Instance Artifact Format

**Role:** Schema Architect | **Layer:** Identity (1), Relationship (3)

### Artifact

Specification document `docs/federation-artifact-format.md` with:
- Complete JSON-LD format for federated artifacts
- Ed25519 signature scheme for provenance
- SHA-256 content hashing for integrity
- TypeScript serializer/deserializer implementations
- SQL export function (`export_artifact_federated()`)
- Security considerations and trust model integration

### Key Decisions

1. **JSON-LD Foundation** — Standards-based format enables interoperability beyond commons.id ecosystem
2. **Ed25519 Signatures** — Fast, small signatures (64 bytes), widely supported
3. **Content Addressing** — SHA-256 hash enables deduplication and integrity verification
4. **Self-Contained Format** — All provenance data travels with artifact (offline-capable)
5. **Pull Over Push** — Receiving instances request content (prevents spam)

### Technical Details

```typescript
interface FederatedArtifact {
  '@context': string;
  '@type': 'Artifact';
  id: string; // URL
  instanceId: string;
  instanceDomain: string;
  type: 'concept' | 'question' | 'resource' | 'method' | 'insight';
  // ... content fields ...
  signature: {
    algorithm: 'ed25519';
    publicKey: string; // base64
    signature: string; // base64
    signedAt: string;
  };
}
```

Canonicalization: JSON with sorted keys, signature computed over SHA-256 of canonical form.

### Future Extensions Identified

- Versioning for artifact evolution tracking
- Binary attachments with content-addressed storage
- JSON Patch for efficient updates
- Encrypted content for private artifacts

## Sprint 91: Federation Protocol Design

**Role:** Technical Lead | **Layer:** All

### Artifact

Protocol specification `docs/federation-protocol.md` defining:
- Instance discovery via DNS TXT records + `.well-known/commons` endpoint
- Trust establishment with 4-level model
- Pull-based artifact synchronization (optional webhook push)
- Deterministic conflict resolution rules
- Instance deactivation flows (graceful + forced)
- Extended data model (`federated_artifacts`, `federation_sync_log`, `federation_conflicts`)
- Complete API endpoint specs with rate limits
- Security considerations and DoS prevention
- Monitoring metrics and alerting

### Key Decisions

1. **DNS-Based Discovery** — Leverage existing infrastructure, no central registry needed
2. **Pull-First Architecture** — Prevents unsolicited spam, gives receivers control
3. **Trust Is Transitive** — Can inherit trust from mutually trusted instances
4. **Conflicts Resolve by Trust Then Time** — Deterministic without central coordination
5. **Audit Everything** — Full logging of trust decisions, conflicts, and imports

### Protocol Flows Defined

1. **Discovery:** DNS TXT → `.well-known/commons` → signature verification
2. **Trust:** Manual verification, out-of-band confirmation, web-of-trust, domain challenges
3. **Sync:** Pull `/api/federation/v1/feed?since=TIMESTAMP`, verify signatures, import
4. **Conflict:** Detect via content hash mismatch, resolve by trust > timestamp > hash
5. **Deactivation:** Graceful POST to `/deactivate` or forced admin removal

### Implementation Roadmap

- **Phase 1 (Sprints 89-92):** Foundation — identity, format, protocol, sharding
- **Phase 2 (Sprints 110-112):** Core sync — discovery, pull sync, identity portability
- **Phase 3 (Sprints 113-116):** Hardening — trust enforcement, conflict automation, monitoring
- **Phase 4 (Sprints 117-120):** Scale — CDN, multi-region, horizontal scaling, chaos testing

## Architectural Insights

### Why Federation Now?

Even though the communication layer is deferred, federation foundations are:
1. **Non-disruptive** — No UI changes, no risk to ETHBoulder stability
2. **Long-lead** — Architecture decisions inform later implementation
3. **Clarifying** — Forces explicit design of trust, identity, and sync models

### Pattern Emergence

Federation maps cleanly onto the Seven Progressive Design Patterns:
1. **Identity** — Instance registry, unique domains, public keys
2. **State** — Artifact content, metadata, sync status
3. **Relationship** — Inter-instance trust, artifact lineage across instances
4. **Event** — Sync operations, conflict detection, trust changes
5. **Flow** — Pull/push synchronization, webhook delivery
6. **Constraint** — Trust levels, rate limits, conflict resolution rules
7. **View** — Federation monitoring dashboard (Sprint 115)

This validates the pattern stack as a universal decomposition.

### JSON-LD Choice

Using JSON-LD (vs. raw JSON) provides:
- **Standards compatibility** — schema.org vocabulary, RDF tooling
- **Semantic clarity** — `@context` makes meaning explicit
- **Future-proof** — Extensible without breaking changes
- **Interop potential** — Bridges to ActivityPub, Solid, other semantic web protocols

Trade-off: Increased payload size (~10-15%), acceptable for federation use case.
